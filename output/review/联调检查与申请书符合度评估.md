**一、现在的实际结构与 Java/IDEA 的影响**

当前 app.py 是 Flask 后端，负责登录、页面、画面接口、人脸上传；algorithm 是 Python 算法。templates 和 static 才是浏览器界面。当前项目不是一个已经调用同学 Java 接口的纯前端。

现有代码的数据流是：浏览器 → Flask 5000 → Python 算法；Java 8080 → MySQL/Redis 是旁边独立的一条链。当前没有从算法向 Java 上报事件的调用，也没有页面调用 /api/v1 的业务请求。

IDEA 是开发工具，和 VS Code、PyCharm 的选择不决定网络接口能否互通。实际需要对齐的是服务地址、Java/Python 运行环境、接口路径、认证、请求体和消息协议。不需要为了 Java 重写成 Vue，也不能把 Jinja 模板直接交给 Java 就期待它自动渲染。

**Java AI 上报接口的真实契约**

接口为 POST /api/v1/ai/events。当前同样受 JWT 拦截保护，没有单独的算法服务认证；不能直接不带认证上报。

| Java 字段 | 必填 | 当前算法情况 / 对接要求 |
|---|---|---|
| eventNo | 是 | 当前缺失；为每个事件生成唯一编号，同一事件重试沿用该编号 |
| eventType | 是 | 映射到四类枚举；emotion → EMOTION_ABNORMAL |
| cameraCode | 是 | 使用数据库存在的业务编号，不直接使用 OpenCV 设备下标 |
| confidence | 是 | 当前未输出；需约定各算法的分数含义，不能把姿态模型检测分数未经说明当成摔倒概率 |
| eventTime | 是 | 使用约定时区的真实日期时间，例如 2026-08-31T14:30:00；当前计时器数值不能用于入库 |
| location | 是 | 来自摄像头/区域配置 |
| description | 是 | 描述事件，避免在前端凭字段猜测 |
| personCode | 否 | 已知人员映射数据库人员编号；当前算法名称与数据库编号未打通 |
| snapshot | 否 | Multipart 文件；上传图片内容，不是 D: 开头的磁盘路径 |

Content-Type 必须是 multipart/form-data；即使没有截图，也要与这个接口声明一致。算法服务后续应使用可续期的专用服务凭据，避免依赖人工登录得到的短期用户 token。

Java 对重复 eventNo 当前返回业务错误“事件已经存在”。客户端重试处理应核实是否为同一事件已入库，不能不断换编号造成重复记录，也不能无条件把所有同名冲突视为成功。

**三、当前 Python/页面的确定性错误**

1. **人脸库更新后，融合算法仍持有旧空列表。** algorithm/yolo_fall_cam.py:14 从 face_emotion_detect 导入列表对象；后者在 :51、:52 重新赋值为新列表。融合模块仍指向原列表。隔离执行实际加载函数后，模块内编码数为 1，融合导入的旧列表长度仍为 0。结果是识别到的人脸无法从这个列表匹配为熟人。建议通过模块/人脸库服务取快照，或受锁保护地原地更新；同时处理上传与检测并发。

2. **摄像头存在三套编号。** yolo_fall_cam.py:23 使用设备下标 0，生成 cam000；video_render.js 将此画面放在 cam001；StructureAndData SQL 唯一摄像头样例为 CAM003。Java 会查询 cameraCode 是否存在，CAM000 不会因“都是第一路”就自动匹配。应分离 captureSource=0 与 cameraCode，并统一前端展示、数据库、算法上报。

3. **告警时间不是日期时间。** yolo_fall_cam.py:71 的 getTickCount/getTickFrequency 是用于计算时间间隔的计时器读数。用它计算速度是合理的，但不能作为 :91 事件发生时间，也不能给 Java LocalDateTime.parse。应同时保留算法计时和真实事件时间两个字段/用途。

4. **截图用磁盘路径充当 URL。** yolo_fall_cam.py:86—92 把本地绝对路径发给网页；socket_base.js:16 将它直接放入 img src。app.py 也没有 uploads 的 HTTP 文件路由。应上传到 Java 使用 /uploads/events/...，或建立经过权限校验的图片服务。跨端口时要统一图片 URL 的服务来源。

5. **摔倒配置参数写了但没有生效。** configs/fall_detection.yaml 的 angle_threshold、velocity_threshold、time_window、min_alert_interval 不属于 FallConfig 的字段，被 from_mapping 静默丢弃。隔离调用实际函数确认：有效下坠阈值仍是默认 0.25，角度仍为默认 60°。应统一字段名、单位及含义，对未知键报错；不能把 time_window 直接假定成某个秒数参数。

6. **上传显示成功不保证录入成功。** face_emotion_detect.py:184 忽略 cv2.imwrite 的返回值，:186 固定返回 True；隔离模拟写入失败仍返回 True。图片没有检测出人脸时，也没有通过有效编码数量阻止“成功”。app.py:102—103 读到 type/note 后未保存。还需处理中文路径写入、唯一人员 ID、同名覆盖、姓名作为路径的安全性、照片格式/尺寸和单人脸校验。

7. **侧栏将情绪告警误报为区域闯入。** socket_base.js 只对 fall、stranger 分支，其他类型默认区域闯入。实际脚本在隔离 JS 环境中重现。Java 的 camelCase 消息原样送入当前渲染函数还会产生 undefined。

8. **“持续负面情绪”目前是一帧悲伤就触发。** yolo_fall_cam.py:124、131 没有按老人累计持续时间，也没有身份维度的时间窗。alert_lock 只是防止连续重复发送；检测结果短暂消失会解锁，不是持续悲伤判定。

9. **有多个人时，摔倒状态机仅处理最大框。** yolo_fall_cam.py:70 的 select_largest_pose 配一个全局状态机。不能认为所有老人都受同等监护；最大目标切换时还可能把不同人的时序混在一起。应给目标稳定 trackId 并维护每人状态机，再关联 personCode。

10. **实时性能有串行阻塞风险。** YOLO、人脸比对、每张人脸的 DeepFace 分析均在同一摄像头循环中，完成后才更新画面。情感推理慢会拖慢画面和下一次摔倒检测；前端 300ms 轮询不会增加后端推理帧率。建议采集与推理解耦、情感低频分析、有界队列丢弃过时帧，再测端到端延迟。本轮没有实测，README 中的帧率数字不作为已验证结果。

**五、Java 后端与数据库也有需要修补的部分**

1. **文档有过期信息。** FRONTEND_INTEGRATION.md 和 KNOWN_ISSUES.md 写未配置 CORS；实际 WebMvcConfig.java:66 已有 addCorsMappings。当前不能把问题直接归因于“未配置跨域”。仍须在实际部署检查 Origin、代理与预检响应，正式环境也不应无限制允许来源。该指南的 Vite 代理例子不适用于当前没有 Vite 的 Flask 工程，可采用统一反向代理。

2. **新事件未清理列表/统计缓存。** AiEventController.java:379 调用 save 后没有清 event:list/event:statistics；EventServiceImpl 仅在更新、删除中清理。若之前命中缓存，列表与统计可能约 60 秒仍显示旧值，而 WebSocket 已收到新事件。应在新增成功后统一失效缓存。

3. **危险区域缺少几何数据。** danger_zone SQL 与 DangerZone 实体只有编号、名称、类型等，没有图像坐标、归一化坐标或多边形。AI 上报也没有 zoneCode 参数，当前从该摄像头启用区域中 LIMIT 1 选一个，多个区域会关联不准确。补区域几何、坐标系/画面尺寸、配置下发，并由算法明确上报命中的区域。

4. **老人档案不是通用人脸库。** elder 表没有人脸照片、编码、人员类别和家属关系；sys_user 也不能替代老人/义工/家属身份库。应制定稳定人员编号和人脸同步机制，不宜将显示姓名作为唯一身份标识。

5. **实时消息存在两种结构。** 新增为 EventWebSocketDTO，状态更新仅有 eventId/eventNo/status/message。建议定义 messageType，并分别新增列表项/更新已有列表项，不能对所有消息都按“新告警”渲染。

6. **/events/latest 返回 JSON 字符串数组。** RedisUtil.range 返回 List<String>，并非已经解析的事件对象列表，而且该读取没有与其他查询一致的降级逻辑。建议返回统一 DTO；不要让每个页面自行猜测是否需要二次 JSON.parse。

7. **开放画面和告警存在权限缺口。** Flask 两个画面 API 没有 session 校验，Socket.IO 无连接鉴权；Java 原生 WebSocket 没有身份/角色校验，uploads 静态资源未受 /api 拦截器保护。应按机构、角色与关联老人授权，增加图片访问控制，移除默认密钥与调试配置。当前不适合直接暴露到公网。

两份 SQL 的 CREATE TABLE 定义经比较相同，是“只含结构”和“结构加样例数据”的选择，不是两个数据库都需要导入。两者含 DROP TABLE IF EXISTS；已有业务数据时直接导入可能覆盖，必须先备份并确认目标库。仅导入结构不会生成可登录用户；真实登录使用数据库里的 BCrypt 密码和用户状态，不能只因为 Flask 的测试密码可用就认为 Java 也可用。

Apifox AI 表单将字段多处标为非必填，而 Java Controller 有多个默认必填的 RequestParam；状态更新样例还写死 /api/v1/events/2/status。应以核对后的实际接口契约更新文档，不能把样例中的 ID、人员编号或摄像头编号原样当成通用配置。
